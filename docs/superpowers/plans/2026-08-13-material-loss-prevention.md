# 자재로스 방지 — 논의 정리 (2026-08-13)

> 이 문서는 **결정된 설계를 정리한 것**이지 구현 계획이 아니다. 코드·마이그레이션
> 실행은 아직 하나도 안 됐다 — 마이그레이션 초안 파일 2개만 만들어뒀다(맨 아래 참고).
> 팀 상의 후 진행 여부·순서를 정하면 된다.

## 배경

재고관리프로그램을 앱에 통합할 예정이라, 이 참에 자재로스(신청↔지급↔설치 수량이
안 맞아 새는 것)를 잡을 방법을 논의했다. 바코드 도입도 검토했으나, 그보다 먼저
**지금 자유텍스트로 뭉쳐 저장되는 부품 정보를 구조화하는 것**이 더 저비용·고효과라는
결론.

## 채택한 방향: 하이브리드

- **고가품(10만원 이상 — PCB·모터·인버터·제어반 등)**: 부품마스터로 추적. 이런
  품목은 어차피 전부 **견적요청(quote_requests)** 채널로만 들어오므로, 부품마스터
  연동도 여기에만 붙인다.
- **저가 소모품**: 지금처럼 자유텍스트 유지, 추적 안 함. 전부 마스터화하면 목록이
  너무 커져서 실용성이 없어진다는 판단.

## 현재 구조에서 로스가 새던 지점

- `material_requests.part`(text)가 자유텍스트라 신청/지급/설치 수량을 시스템이
  비교할 방법이 없었다.
- 재고 카운트는 `kit_stock`(기사별 상비부품)뿐인데, 이것도 기사가 "사용함" 체크로
  자진신고하는 값이라 스캔 검증이 없다.
- 중앙 창고 개념 자체가 스키마에 없어서 대조할 기준점이 없다.
- 견적요청의 "자재지급완료"는 담당 기사에게 할일이 자동생성되는 시점일 뿐,
  실제 종점(로스 추적 관점에서 "설치 확정")은 그 할일이 **비용청구로 완료 처리되는
  시점**이다 — 이 둘을 헷갈리면 안 된다.

## 데이터 구조 변경 계획

| 대상 | 변경 | 이유 |
|---|---|---|
| `material_requests` | `part_rows`(jsonb) 추가 | 신청 폼(`PartsRowsInput`)이 이미 `{name, qty}` 행으로 입력받는데, 저장 시 `formatPartRows()`로 문자열로 합쳐지던 걸 구조 그대로 저장 |
| `todos` | `billing_part_rows`(jsonb) 추가 | 관리자가 신청과 다르게 지급했을 때 그 확정값을 구조화해서 남김. 기존 `billing_part`(text, 024에서 이미 생성)는 있는데 화면 어디서도 실제로 안 쓰이고 있었다 |
| `quote_items` (jsonb 배열, 기존) | `partId`, `returnRequired` 키 추가 | 마이그레이션 불필요(jsonb) — 고가부품 항목만 마스터 연결 + 폐자재 반납여부 |
| `parts_master` | 신규 테이블 | 고가부품 카탈로그 (`name`, `category`, `default_price`, `default_return_required`) |

## 비용청구 프리필 원칙

**"기사가 신청한 값"이 아니라 "관리자가 최종 확정한 값"을 프리필 기준으로 삼는다.**

- **자재신청건**: 관리자가 지급 처리할 때 신청값 그대로 두거나 수정한
  `billing_part_rows`/`billing_amount` → 이게 할일 표시와 청구 화면 프리필의
  공통 소스. (지금은 `billingAmount`가 참고 텍스트로만 보이고 실제 입력창엔 안
  들어가 있어서, 확인한 숫자를 기사가 다시 타이핑해야 하는 상태.)
- **견적요청건**: 애초에 관리자가 "작성" 단계에서 항목·수량을 직접 정하는
  구조라 `quote_items` 자체가 이미 확정값이다 → 부품명·수량을 청구 화면에
  프리필. **금액은 지금처럼 "견적서 참조"로 유지**(재입력·재확인 없음).
- 참고: 실측상 신청/견적대로 그대로 설치되는 비율이 80% 이상이라, 프리필의
  체감 효과가 클 것으로 판단.

## 로스리포트 — 기존 대시보드 KPI와의 관계

새 메커니즘이 아니라 기존 "지급 후 30일 초과 미청구" KPI
(`Dashboard.jsx`, `overdueUnbilled`)의 **부분집합 + 상세 뷰**다.

- 기존 KPI: `material`+`quote` 소스 전체, 가격 무관, 카운트만.
- 로스리포트: 견적건 중 `quote_items`에 `partId`(고가부품)가 있는 것만 필터링,
  "무슨 부품이 얼마짜리가 며칠째 안 걷혔는지" 항목·금액 단위 상세 리스트로 표시.
- 구현 시 새 쿼리보다는 기존 `overdueUnbilled` 로직에 필터 조건을 얹는 방식이
  자연스럽다.

## 폐자재 반납 흐름

1. 견적 작성 시 고가부품 항목(`partId` 연결된 것)마다 `returnRequired` 체크 —
   `parts_master.default_return_required`로 초기값 자동 채움 가능(PCB·모터 등).
2. 비용청구 제출(= 시공확인 완료) 시점에 `returnRequired: true`인 항목이 있으면
   `todos.source = "waste_return"` 할일을 자동생성 (부품별로 1건씩, `quoteRequestId`
   연결, 담당자 = 방금 청구한 기사).
3. 완료 방식은 기존 "관리자 부여"(`source === "manual"`) 계열의 셀프완료 패턴을
   재사용하되, **반납사진(`photoUrls`)이 없으면 "완료 처리" 버튼 비활성화** 조건만
   추가.
4. (선택) 대시보드 "30일 초과 미청구" 필터에 `waste_return`도 포함시키면 폐자재
   미반납도 같은 화면에서 관리 가능.

## 아직 정해지지 않은 것 / 논의 필요

- `parts_master` 초기 데이터를 기존 재고관리프로그램에서 어떻게 가져올지
  (엑셀 export? API 있는지?)
- "기타/직접입력"으로 들어온 신규 고가부품을 누가/어떤 기준으로 마스터에
  승인·추가할지
- 화면 구현 우선순위: A(자재신청 구조화+프리필)가 스키마 변경이 작고 효과가
  바로 체감되니 먼저, C(부품마스터·견적 연동·폐자재반납)는 별도 단계로 진행하는
  게 자연스러워 보임 — 이건 제안일 뿐 팀 상의 필요.
