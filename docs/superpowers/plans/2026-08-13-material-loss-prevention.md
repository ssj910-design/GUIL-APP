# 자재로스 방지 — 논의 정리 (2026-08-13)

> **2026-08-19: 최신 설계는 [2026-08-19-material-loss-prevention-design.md](../specs/2026-08-19-material-loss-prevention-design.md)로 정리됨** — 이 문서는 그 이전 논의 이력.
>
> 이 문서는 **결정된 설계를 정리한 것**이지 구현 계획이 아니다. 코드·마이그레이션
> 실행은 아직 하나도 안 됐다 — 마이그레이션 초안 파일 2개만 만들어뒀다(맨 아래 참고).
> 팀 상의 후 진행 여부·순서를 정하면 된다.

## 배경

재고관리프로그램을 앱에 통합할 예정이라, 이 참에 자재로스(신청↔지급↔설치 수량이
안 맞아 새는 것)를 잡을 방법을 논의했다. 바코드 도입도 검토했으나, 그보다 먼저
**지금 자유텍스트로 뭉쳐 저장되는 부품 정보를 구조화하는 것**이 더 저비용·고효과라는
결론.

## 채택한 방향: 하이브리드

- **고가품(10만원 이상 — PCB·모터·인버터·제어반 등)**: 부품마스터로 추적. 이런
  품목은 어차피 전부 **견적요청(quote_requests)** 채널로만 들어오므로, 부품마스터
  연동도 여기에만 붙인다.
- **저가 소모품**: 지금처럼 자유텍스트 유지, 추적 안 함. 전부 마스터화하면 목록이
  너무 커져서 실용성이 없어진다는 판단.

## 현재 구조에서 로스가 새던 지점

- `material_requests.part`(text)가 자유텍스트라 신청/지급/설치 수량을 시스템이
  비교할 방법이 없었다.
- 재고 카운트는 `kit_stock`(기사별 상비부품)뿐인데, 이것도 기사가 "사용함" 체크로
  자진신고하는 값이라 스캔 검증이 없다.
- 중앙 창고 개념 자체가 스키마에 없어서 대조할 기준점이 없다.
- 견적요청의 "자재지급완료"는 담당 기사에게 할일이 자동생성되는 시점일 뿐,
  실제 종점(로스 추적 관점에서 "설치 확정")은 그 할일이 **비용청구로 완료 처리되는
  시점**이다 — 이 둘을 헷갈리면 안 된다.

## 비용청구 프리필 원칙

**"기사가 신청한 값"이 아니라 "관리자가 최종 확정한 값"을 프리필 기준으로 삼는다.**

- **자재신청건**: 관리자가 지급 처리할 때 신청값 그대로 두거나 수정한
  `billing_part_rows`/`billing_amount` → 이게 할일 표시와 청구 화면 프리필의
  공통 소스. (지금은 `billingAmount`가 참고 텍스트로만 보이고 실제 입력창엔 안
  들어가 있어서, 확인한 숫자를 기사가 다시 타이핑해야 하는 상태.)
- **견적요청건**: 애초에 관리자가 "작성" 단계에서 항목·수량을 직접 정하는
  구조라 `quote_items` 자체가 이미 확정값이다 → 부품명·수량을 청구 화면에
  프리필. **금액은 지금처럼 "견적서 참조"로 유지**(재입력·재확인 없음).
- 참고: 실측상 신청/견적대로 그대로 설치되는 비율이 80% 이상이라, 프리필의
  체감 효과가 클 것으로 판단.

## 로스리포트 — 기존 대시보드 KPI와의 관계

새 메커니즘이 아니라 기존 "지급 후 30일 초과 미청구" KPI
(`Dashboard.jsx`, `overdueUnbilled`)의 **부분집합 + 상세 뷰**다.

- 기존 KPI: `material`+`quote` 소스 전체, 가격 무관, 카운트만.
- 로스리포트: 견적건 중 `quote_items`에 `partId`(고가부품)가 있는 것만 필터링,
  "무슨 부품이 얼마짜리가 며칠째 안 걷혔는지" 항목·금액 단위 상세 리스트로 표시.
- 구현 시 새 쿼리보다는 기존 `overdueUnbilled` 로직에 필터 조건을 얹는 방식이
  자연스럽다.

## 폐자재·여유부품 반납 흐름 (2026-08-18 갱신 — 여유부품 개념 통합)

재고관리(`inventory_products`/`inventory_stock_movements`)가 실제로 생기면서, 불량 대비로
여유 있게 가져가는 부품("여유부품")도 같이 추적해야 한다는 논의가 나왔다. 폐자재(교체하며
나온 헌 부품)와 여유부품(안 쓰고 남은 새 부품)은 성격은 다르지만 **"창고에서 나갔는데 고객
현장에 안 남은 것"**이라는 점에서 같다고 보고, 같은 반납 메커니즘 하나로 묶기로 했다.

**여유부품**: 견적 항목의 수량은 지금 하나(`qty`, 견적서에 찍히는 설치확정수량=고객
청구수량)뿐이라, 여기에 **실제 창고에서 반출한 수량**(`qtyTaken`)을 별도로 받는다. 안
채우면 `qty`와 같다고 간주(대부분은 여유 없이 그대로 쓰니 기본값 재입력 부담 없게).
여유분 = `qtyTaken - qty`.

**흐름**:
1. 견적 작성 시 고가부품 항목(`partId` 연결된 것)마다 `returnRequired` 체크 + `qtyTaken`
   입력(여유 있으면 `qty`보다 크게).
2. **자재지급완료**(`handleCompleteQuoteSupply`) 시점 — 실제로 부품이 창고에서 기사
   손으로 넘어가는 순간 — `partId` 있는 항목마다 `qtyTaken`만큼 `inventory_stock_movements`에
   'out' 기록.
3. **비용청구 제출**(= 시공확인 완료) 시점에 `returnRequired: true`이거나
   `qtyTaken > qty`인 항목이 있으면 `todos.source = "waste_return"` 할일을 자동생성
   (부품별로 1건씩, `quoteRequestId` 연결, 담당자 = 방금 청구한 기사). 반납수량 =
   폐자재개수(`returnRequired`면 보통 1) + 여유분(`qtyTaken - qty`).
4. **기사 완료**: 기존 "관리자 부여"(`source === "manual"`) 계열 셀프완료 패턴 재사용,
   **반납사진(`photoUrls`)이 없으면 "완료 처리" 버튼 비활성화**. 이 시점엔 재고에
   아직 반영 안 됨 — `done=true`와 재고 반영은 분리된 이벤트(아래 참고).
5. **관리자 확인 — 여기서만 재고에 실제 반영된다**: `TodosAdmin.jsx`에
   `source==="waste_return" && done && !stockConfirmedAt` 필터 뷰를 추가. 관리자가
   반납사진과 확인수량(기본값=요청수량, 실물과 다르면 수정 가능)을 검토 후 "확인"을
   누르면:
   - **수량이 맞으면**: 확인수량만큼 'in' 기록 + `stock_confirmed_at` 채우고 종료.
   - **모자라면**: 확인된 만큼만 먼저 'in' 반영, 남은 수량(`요청수량 - 확인수량`)으로
     할일 제목·필요수량을 갱신하고 `done=false`로 **재오픈** → 기사가 나머지를 재반납
     → 4번부터 반복. 사진은 재오픈마다 지우지 않고 누적(1차/2차 제출 이력 남김).
6. (선택) 대시보드 "30일 초과 미청구" 필터에 `waste_return`도 포함시키면 미반납도 같은
   화면에서 관리 가능.

기사 쪽 "완료"(사진 제출)와 재고 반영(관리자 확인)을 분리한 이유: 기사가 사진만 올리고
실물을 안 보냈거나 개수가 다른 경우를, 재고에 잘못 반영되기 전에 관리자 확인 단계에서
걸러내기 위함.
