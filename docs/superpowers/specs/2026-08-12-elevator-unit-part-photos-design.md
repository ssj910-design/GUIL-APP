# 승강기 부품현황 사진 Design

## 목표

승강기정보 탭(호기 단위)에 "부품현황" 서브탭을 추가한다. 기사가 이 호기에 실제로
설치된 부품 사진을 대분류·중분류·세부항목별로 찍어 올리고, 나중에 다른 기사도
같은 자리에서 바로 확인할 수 있게 한다. 목적은 사고 증거가 아니라 "지금 이 승강기에
뭐가 달려 있는지" 참조용 사진첩 — 출동 전 확인, 부품 발주 시 스펙 확인 등에 쓴다.

## 배치

`app/components/tabs/SiteTab.jsx`의 `ElevatorDetailScreen`(승강기정보 화면)은 이미
호기 단위로 정보/고장/검사/부품교체내역/견적내역 5개 서브탭을 스와이프로 넘기는
구조다(`elevatorSubTabs` 배열, `SwipeSubtabTrack`). 여기에 "부품현황"을 6번째
서브탭으로 추가한다 — 부품교체내역(청구 이력) 바로 뒤, 견적내역 앞.

`부품교체내역`(billings 청구 이력)과는 완전히 다른 개념이라 기존 탭을 확장하지
않고 새 탭으로 분리한다.

## 부품 분류 체계 (고정)

현장마다 부품 구성이 달라지는 게 아니라 회사가 정한 고정 점검 항목이므로, DB가
아니라 코드 상수(`lib/constants.js` 또는 신규 파일)로 관리한다. 카테고리마다
깊이가 다르다 — 어떤 대분류는 중분류를 한 겹 더 갖고, 어떤 대분류는 세부항목이
바로 붙는다. 아래가 확정된 전체 목록:

```
1. 기계실
   1) 제어반: 전체사진, PCB, 인버터, ARD, 마그네트, SMPS
   2) 권상기: 전체사진, 구동기, 권상기, 브레이크
   3) 조속기: 전체사진, 조속기 스위치
   4) 비상통화장치            ← 중분류 없이 대분류 바로 아래 리프
2. 카 상부                    ← 중분류 없음, 리프 4개가 바로
   전체사진, 카탑PCB, 랜딩스위치, 가이드슈/가이드롤러/오일러
3. 카도어                     ← 중분류 없음
   도어드라이브, 도어모터·벨트, 카도어 인터록, 카도어 벤, 카도어 씰
4. 승장도어                   ← 중분류 없음
   행거플레이트, 승장도어 인터록, 승장도어 씰
5. 승강장                     ← 중분류 없음
   승장버튼, 승장인디게이터
6. 카 내부
   1) 조작반: 전체사진, 버튼, 통신보드, 카 인디게이터
   2) 조명등                  ← 중분류 없이 리프
7. 승강로                     ← 중분류 없음
   리미트스위치, 조속기 인장풀리, 완충기 스위치, 피트 조작반
```

리프(세부항목)가 실제 사진을 올리는 단위다. 이 목록을 표현하는 자료구조는
재귀적으로 짠다 — `children`이 문자열 배열이면 리프, 문자열이 아니라
`{ label, children }` 객체 배열이면 한 겹 더 중분류가 있는 것으로 처리해서,
기계실처럼 중분류가 있는 경우와 카상부처럼 없는 경우를 같은 렌더 함수 하나로
처리한다(트리 깊이가 카테고리마다 달라도 컴포넌트는 하나).

## UI 구조

3단(또는 2단) 아코디언 — 대분류 → (중분류) → 리프.

- **대분류 행**: 라벨 + 배지("채워진 리프 수/전체 리프 수", 이 대분류 아래 모든
  후손 리프를 합산) + 화살표. 아이콘 없음. 탭하면 펼침/접힘.
  `app/components/tabs/AdminTab.jsx`의 `AccordionRow`와 동일한 상호작용 —
  현재 AdminTab.jsx 안에 로컬로만 정의돼 있어 SiteTab.jsx에서 못 쓰므로,
  공용 위치(`app/components/formWidgets.jsx` 또는 `adminShared.jsx`)로 옮기거나
  같은 모양의 컴포넌트를 하나 더 둔다.
- **중분류 행**: 대분류 행보다 한 단계 들여쓰기, 글자 살짝 작게. 라벨 + 배지(같은
  방식으로 그 중분류 안 리프만 합산) + 화살표. 탭하면 펼침/접힘.
- **리프 행**: 라벨 + 상태("N장", 녹색 / "사진 없음", 회색) + 화살표. 탭하면
  그 자리에서 펼쳐지고 안에 사진 그리드가 나타난다.
- **리프 안 사진 그리드**: 기존 `app/components/admin/adminShared.jsx`의
  `FileCarousel`을 재사용한다 — 이미 여러 장 첨부, 확대(탭하면 큰 화면), 개별
  삭제, "추가" 버튼을 다 갖추고 있다. 문서 첨부(계약서 등)와 다르게 여기는 사진만
  필요하므로 `accept="image/*"`로 좁혀서 쓴다. 빈 슬롯이면 "촬영/선택" 버튼 하나,
  채워지면 썸네일 여러 장 + 추가 버튼.

번호 접두어("1)", "2)")는 화면에 표시하지 않는다 — 라벨만.

## 데이터 모델

사진 1장 = 1행인 새 테이블. 각도별로 여러 장 계속 쌓일 수 있어서 `units`/`sites`
테이블에 JSON 배열 컬럼을 얹는 기존 방식(`contractUrls` 등) 대신, `self_checks`·
`kit_stock`처럼 사실 하나당 한 행인 테이블로 둔다 — 배열 읽고-수정하고-다시쓰기
경합 없이 추가/삭제가 단순해진다.

```sql
create table public.unit_part_photos (
  id uuid primary key default gen_random_uuid(),
  unit_id uuid not null references public.units(id) on delete cascade,
  category text not null,      -- 대분류, 예: '기계실'
  subcategory text,             -- 중분류, 예: '제어반' — 없으면 null
  part text not null,           -- 리프(세부항목), 예: 'PCB'
  url text not null,
  uploaded_by uuid references public.profiles(id),
  created_at timestamptz not null default now()
);
create index on public.unit_part_photos (unit_id);
```

사진 파일 자체는 기존 `photos` Storage 버킷에 `uploadPhoto()`(`lib/photos.js`)로
올린다 — 폴더 경로 `unit-parts/${unit.id}/${category}/${subcategory ?? "_"}/${part}`.
Storage RLS는 기존 `photos` 버킷 정책(anon, authenticated 모두 허용, 마이그레이션
110)을 그대로 쓰고 별도 정책이 필요 없다.

`unit_part_photos` 테이블 RLS는 기존 `units`/`self_checks` 등과 동일한 수준
(로그인한 기사·관리자면 읽기/쓰기 가능)으로 맞춘다.

## 배지 집계 로직

- 리프: 그 리프에 딸린 사진 개수로 "N장"/"사진 없음" 표시.
- 중분류: 그 중분류 아래 리프 중 사진이 1장이라도 있는 리프 수 / 전체 리프 수.
- 대분류: 대분류 아래 모든 리프(중분류를 거치든 안 거치든) 중 사진이 1장이라도
  있는 리프 수 / 전체 리프 수.

## 범위 밖

- 사진 촬영 시각/버전 이력 UI(현재는 삭제하면 그냥 없어짐 — 과거 사진을 남기고
  싶으면 지우지 않고 계속 추가하면 됨, 별도 "이력" 화면은 안 만듦)
- 이 탭에서 부품 발주·재고 연동 (자재신청과는 별개 기능)
- 관리자 콘솔(PC)에서의 별도 화면 — 우선 모바일 앱(SiteTab)에만 추가하고, 필요성
  확인되면 나중에 관리자 콘솔에도 붙인다.
